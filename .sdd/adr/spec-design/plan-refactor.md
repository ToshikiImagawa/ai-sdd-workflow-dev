# リファクタリング計画 決定ログ

## 2026-07-08 既存仕様書の有無で Case A / Case B に分岐する

- **Decision**: 既存仕様書がある場合（Case A）は既存仕様を土台に分析し、無い場合（Case B）はテンプレートから逆生成する、2 つの処理フローに分岐させる。
- **Rationale**: 既存仕様書がある場合は逆生成よりも既存仕様を土台にした分析の方が効率的かつ安全であり、無い場合は逆生成しなければ明確な文書が得られない。ロジックは複雑になるが、安全性と柔軟性が上がるトレードオフを取る。
- **Rejected alternatives**: 常に逆生成する — 既存仕様書を上書きしてデータ喪失のリスクがあるため却下。常に既存ドキュメントを参照する — 仕様書が無い既存実装に対応できないため却下。

## 2026-07-08 context パラメータをオプションにする

- **Decision**: リファクタリングの観点を示す `context` パラメータを必須ではなくオプションとする。
- **Rationale**: context 無しの自動分析でも一般的な改善提案は可能であり、指定すればより焦点を絞った計画が作れる。必須にしない方が使い勝手が良い。実装上は context の有無で異なるプロンプトを用意する複雑性を受け入れる。
- **Rejected alternatives**: None considered

## 2026-07-08 実装ファイルが 20 件を超える場合はユーザー確認を必須にする

- **Decision**: 分析対象の実装ファイルが 20 件以上の場合、処理続行のユーザー確認を必須とする（`--scope` で絞り込み可能）。
- **Rationale**: 分析時間の増加を予防し、不要なファイル読み込みを避けるため。
- **Rejected alternatives**: 固定値でフィルタリングする — ユーザーの意図を反映できないため却下。常にすべて読む — 対象規模が大きいとスケールしないため却下。

## 2026-09-02 Case 判定基準を設計書の有無から仕様書の有無へ移行する

- **Decision**: Case A / Case B の判定を `specification/*_design.md` の有無ではなく、仕様書（`specification/*_spec.md`）の有無で行う。
- **Rationale**: 技術設計書が永続文書ではなくチケット単位の一時ドラフトになったため、「設計書が無い」は正常な状態であり判定基準として成立しない。据え置くと常に Case B に落ち逆生成が無条件に走ってしまう。仕様書は永続文書であり、「仕様が整備済みか」はリファクタリング計画の前提として意味を持つ。判定に使うパスがサフィックス有無の 2 通りに増える代償は、新方針との整合性で相殺される。
- **Rejected alternatives**: 設計ドラフトの有無で判定する — チケット単位のため、同一機能を別チケットで扱うと毎回 Case B になるため却下。Case B を廃止する — 「PRD は無いが実装がある」既存機能を仕様化する唯一の導線が失われるため却下。

## 2026-09-02 逆生成成果物の永続性を成果物ごとに分けて配置する

- **Decision**: 逆生成した仕様書は `specification/` に永続化し、逆生成した設計とリファクタリング計画は `task/{ticket-number}/design-draft.md` に一時配置する。
- **Rationale**: 仕様書（抽象的な「何を」）は実装のリファクタリングでは変わらないため永続化に値する一方、設計とリファクタリング計画（具体的な「どう」）はチケットに紐づく作業計画であり実装完了時点で役目を終える。確定した決定のみを `adr/` に残すことで、古い計画が永続文書として残り続ける問題を避けられる。チケット番号の入力が必要になる代償は、ドキュメントのライフサイクルの一貫性で相殺される。
- **Rejected alternatives**: 両方を永続化する — 新方針が非永続化した設計書を再生産してしまうため却下。両方を一時ドラフト化する — 逆生成仕様書が実装完了時に失われ、仕様の整備が無駄になるため却下。
