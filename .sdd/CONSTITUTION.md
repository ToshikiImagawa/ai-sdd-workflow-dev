# プロジェクト原則

**バージョン**: 2.3.0
**最終更新日**: 2026-10-21
**ステータス**: 有効

## 目的

このドキュメントは、`ai-sdd-workflow` リポジトリ（Claude Code プラグイン・マーケットプレイス）の開発を統制する非交渉原則と基準を定義します。すべてのドキュメント、スキル、エージェント、スクリプト、設計判断はこれらの原則に従う必要があります。

## プロジェクト特性

本プロジェクトは一般的なWebアプリケーションではなく、**Claude Code プラグイン**（Markdown プロンプト、JSON マニフェスト、Bash/Python スクリプトで構成）のマーケットプレイスです。原則はこの特性に合わせて定義しています。

## 原則階層

```
1. ビジネス原則（最優先）
   ↓
2. アーキテクチャ原則
   ↓
3. 開発手法原則
   ↓
4. 技術制約
```

優先度が高い原則が低い原則に優先します。

## 1. ビジネス原則（最優先）

### B-001: Vibe Coding防止

**原則**: 曖昧な指示（「いい感じに」「適当に」「前と同じように」等）による仕様の暗黙的推測を排除し、仕様書を真実の源（Single Source of Truth）とする

**適用範囲**: すべてのスキル・エージェントの設計、およびプラグイン利用者への提供機能

**検証方法**:

- [ ] 曖昧な指示を検出する仕組み（vibe-detector）が機能を損なわずに維持されている
- [ ] 新規スキル追加時、仕様書なしでの実装を許容する設計になっていないか

**違反例**:

- 仕様書チェックを省略できる抜け道を持つスキルを追加する
- 「Vibe Coding防止」を謳いながら曖昧指示を許容するデフォルト動作にする

**準拠例**:

- clarify / vibe-detector スキルとの連携を前提に新機能を設計する

---

### B-002: 多言語対応（EN/JA）の一貫性

**原則**: `SDD_LANG` 環境変数によるEN/JA切り替えをすべてのテンプレート・出力で一貫させる

**適用範囲**: `templates/{en,ja}/` を持つ全スキル、CHANGELOG、README

**検証方法**:

- [ ] 新規テンプレート追加時、`en` と `ja` の両方を作成しているか
- [ ] 出力言語がテンプレート言語と一致しているか（ユーザーのグローバル言語設定で上書きしない）

---

## 2. アーキテクチャ原則

### A-001: Skills-First（Legacy Commands非推奨）

**原則**: 新規コマンドは `skills/` として実装し、`commands/`（legacy）は追加しない

**適用範囲**: 新規機能追加全般

**検証方法**:

- [ ] 新規コマンドが `skills/{name}/SKILL.md` 形式で実装されているか
- [ ] `plugin.json` の該当フィールドに登録されているか

**違反例**:

- 新規に legacy `commands/` ディレクトリへ追加する

**準拠例**:

- `plugins/sdd-workflow/skills/{name}/` にSKILL.mdとtemplates/を配置

---

### A-002: フックとスクリプトの責務分離（Shell/Python + Claude の2フェーズ実行）

**原則**: 静的なファイル操作（コピー・スキャン・環境変数エクスポート）はShell/Pythonスクリプトに委譲し、Claude自身は判断・生成・レビューに専念する

**適用範囲**:

- `sdd-init`, `constitution`, `check-spec` 等の複数ステップスキル
- skills/agents による `.sdd/` ドキュメントの横断読み込み
- AI-SDD原則文書（`AI-SDD-PRINCIPLES.md`）の参照
- スクリプト化できる決定的な走査

**検証方法**:

- [ ] ファイルの存在確認・コピー・削除等の決定的操作がスクリプト化されているか
- [ ] Claudeの処理はスクリプトの出力を読み取って判断する設計になっているか
- [ ] `.sdd/` の横断読み込みは、index が有効なら `index.md` の1回Readで済ませているか
- [ ] 原則文書は必要な節のみを読み、全文Readを繰り返していないか
- [ ] 上記の削減によって、網羅性・品質（検出すべき不整合の見落とし等）を損なっていないか

**違反例**:

- ファイルコピーのような決定的操作をClaudeのツール呼び出しで逐次実行し、トークンを浪費する
- 原則文書の全文Readを繰り返す
- index があるのに、個別のGlob/Grepを重ねて同じ情報を取り直す

**準拠例**:

- `scripts/init-structure.sh` がファイル操作を担い、Claudeは結果を検証・報告する
- `index.md` を1回Readして横断検査を行う（全文が必要な箇所のみ個別ファイルをRead）
- `§ 見出し` を指定して原則文書の必要な節のみReadする

## 3. 開発手法原則

### D-001: Specification-Driven

**原則**: 仕様書（`*_spec.md`）・技術設計書（`task/{ticket-number}/design-draft.md`）なしで実装しない

**適用範囲**: プラグイン自体の新機能・変更すべて

**検証方法**:

- [ ] `.sdd/specification/` に対応する `_spec.md` が存在する
- [ ] `.sdd/task/{ticket-number}/design-draft.md`（技術設計書の一時ドラフト）が生成されている
- [ ] 仕様書が実装前に更新されている

**違反例**:

- 口頭指示のみでスキル・エージェントを実装開始する

**準拠例**:

- Specify → Plan → Tasks → Implement のフローを遵守する

---

### D-002: ファイル命名規則の厳守

**原則**: `requirement/` はサフィックスなしというAI-SDD命名規則を維持する。`specification/` / `adr/` は単一種別ディレクトリであり、ディレクトリのみで種別を識別できるため `_spec` / `-decisions` サフィックスは任意とする（付与してもよいが必須ではない）

**適用範囲**: `.sdd/` 配下のすべてのドキュメント生成処理

**検証方法**:

- [ ] スキルが生成するファイル名が命名規則表（CLAUDE.md参照）と一致しているか
- [ ] `requirement/` 配下のファイルに `_spec` / `_design` サフィックスが付与されていないか

---

### D-003: ドキュメント永続性ルールの遵守

**原則**: `task/` は一時ディレクトリであり、実装完了後に重要な設計判断を ADR（`adr/{feature}.md`）に統合してから削除する

**適用範囲**: `task-cleanup` スキルおよび関連処理全般

**検証方法**:

- [ ] `task-cleanup` 実行前に設計判断の統合漏れがないか確認する

---

## 4. 技術制約

### T-001: JSON/Markdown構文の正当性

**原則**: `plugin.json` / `marketplace.json` は常に正当なJSONであり、Markdownドキュメントはリンク切れを起こさない

**適用範囲**: すべてのプラグイン設定ファイルとドキュメント

**検証方法**:

- [ ] `cat plugins/*/.claude-plugin/*.json | jq .` がエラーなく通る
- [ ] ドキュメント内の相対リンクが有効である

**違反例**:

- コンマ抜け等で不正なJSONをコミットする
- リンク先ファイルをリネーム・削除した際に参照を更新しない

**準拠例**:

- 変更後に `jq` によるJSON構文チェックを実行する

---

### T-002: plugin.json登録の徹底

**原則**: 新規エージェントを追加した場合、必ず `plugin.json` の `agents` に登録する。逆に、標準パスが自動検出されるコンポーネント（`skills/`, `hooks/hooks.json`）は `plugin.json` に宣言しない。また `agents/` にはエージェント定義の `*.md` のみを置き、テンプレート・参照資料・利用例などのサポートファイルは `shared/` 配下に置く

**適用範囲**: `agents/` への新規追加（登録必須）／`skills`・`hooks` フィールド（宣言禁止）／`agents/` の内容（エージェント定義のみ）

**根拠**: Claude Code のマニフェストフィールドは挙動が2種類に分かれる。

| フィールド | 挙動 | 帰結 |
|:---|:---|:---|
| `agents` | 既定の `agents/` 走査を**置換**する | 配列に載せないファイルは読み込まれないため登録必須。なお `agents/` 配下のサポートファイルは誤検出を招くため配置自体を禁止する（下記参照） |
| `skills` | 既定の `skills/` 走査に**加算**する | 標準パスは常に走査されるため `"./skills"` の宣言は冗長 |
| `hooks` | 既定パスを**補完**する（上書きしない） | 標準パスを宣言すると同一ファイルの二重ロードになり、ローダーが `Duplicate hooks file detected` で拒否する |

`agents` 配列はロード対象を決めるだけで、検証系の走査対象は絞れない。`claude plugin validate --strict` は
マニフェストを無視して `agents/**` を再帰走査するため、`agents/` 配下に置いたサポートファイルはエージェント定義として
扱われ検証エラーになる。したがってサポートファイルは `shared/` に置き、エージェント本文からは
`${CLAUDE_PLUGIN_ROOT}/shared/...` 形式で参照する。

**検証方法**:

- [ ] 新規エージェント追加後、`plugin.json` の diff に対応する登録が含まれているか
- [ ] `plugin.json` に `skills` / `hooks` フィールドが無いこと（`scripts/plugin-lint.sh` の Check 4 が機械検証する）
- [ ] `agents/` にサブディレクトリが無く、`agents/*.md` がすべて front matter を持つこと（同 Check 4.2 が機械検証する。ローカルでは `claude plugin validate ./plugins/sdd-workflow --strict` でも確認できる）

---

### T-003: 日本語出力の文字化け防止

**原則**: 日本語テキストに U+FFFD（�）や文字化けパターン（mojibake）を含めない。マルチバイト文字を途中で切断しない

**適用範囲**: 日本語テンプレート・生成ドキュメントすべて

**検証方法**:

- [ ] 出力前に文字化けパターンの混入がないか確認する

---

## 原則追加のガイドライン

新しい原則を追加する際は、以下を考慮してください：

### 良い原則の条件

| 条件        | 説明                         |
|:----------|:---------------------------|
| **検証可能**  | チェックリストで検証できること            |
| **明確**    | 曖昧さがなく、準拠/違反の判断が明確であること    |
| **正当化可能** | なぜその原則が必要かが説明できること         |
| **実現可能**  | チーム全体が実践できること              |
| **永続的**   | 一時的な方針ではなく、長期的に守るべき原則であること |

### 追加プロセス

```
1. 提案（Issue等で議論）
   ↓
2. チーム承認
   ↓
3. 原則ファイルに追加
   ↓
4. バージョンを更新（既存の準拠を壊さないならマイナーアップ。例: 1.0.0 → 1.1.0。
   新原則により既存の実装が違反になる場合はメジャー。区分は「セマンティックバージョニング」を参照）
   ↓
5. 影響を受けるドキュメントを更新
   ↓
6. /constitution validate で検証
```

## コンプライアンス

### 適用メカニズム

**自動化**:

- `session-start` フックによるバージョン整合性チェック
- `plugin-lint` スキルによるプロンプトファイル構文検査

**手動**:

- PRレビュー（`plugin.json` 登録漏れ、命名規則違反の確認）
- `/constitution validate` による仕様書・設計書のコンプライアンス確認

### 違反への対処

| 重大度    | 対応                 | 例                       |
|:-------|:-------------------|:-------------------------|
| **重大** | 即座にマージをブロック        | 不正なJSON、plugin.json未登録   |
| **主要** | 明示的な正当化が必要         | 仕様書なしでの実装               |
| **軽微** | 現在のPRまたはフォローアップで修正 | 軽微なドキュメント表現の修正          |

### 例外プロセス

原則の遵守が不可能な場合：

1. **文書化**: 該当する技術設計書（`task/{ticket-number}/design-draft.md`）に例外理由を記載
2. **正当化**: なぜ原則に従えないか説明
3. **レビュー**: PRレビューで承認を得る
4. **追跡**: `CHANGELOG.md` に記録

## 変更履歴

### v2.3.0 (2026-10-21)

**バージョン区分の定義の統一（マイナー改定。原則本体は変更しない）**

- 区分の定義をオーナー決定の 3 区分に統一した: メジャー = 破壊的変更 / マイナー = 機能追加・更新 / パッチ = 修正。
  追加プロセス節、改定プロセス節、セマンティックバージョニング表で食い違っていた定義
  （「新しい原則の追加」がマイナー／メジャーで矛盾）を解消した
- 判断の目安: これまで準拠していたものが違反になるならメジャー。新原則の追加や適用範囲の拡大でも、
  既存の実装が違反になる場合はメジャーとする。逆に、意味が変わっても既存の実装を違反にしない緩和はマイナー（Issue #196）
- 判定手順: 改定 PR の説明に「既存実装への影響の有無とその根拠」を書き、レビュアーが区分を確認する
- 改定プロセス: メジャーの手順（Issue 先行、実装と不可分な場合の PR 内完結の例外）は、
  メジャーの定義のみ「破壊的変更」に変えて維持した
- 区分の根拠: 既存の準拠を壊さない定義の明確化のためマイナー
- 過去の変更履歴（v2.0.0〜v2.2.0）の区分は書き換えていない

**A-002 の適用範囲の明確化（マイナー改定。原則の主旨は変更しない）**

- 影響: `plugin.json` から `skills` フィールドを削除。`.sdd/specification/` 配下の

## 改定プロセス

### パッチバージョン (x.y.Z)

**対象範囲**: 修正（誤字・表現の修正、リンク修正など、意味を変えない修正）

**プロセス**: PRで変更を提案し、レビュー承認後にバージョンを更新する

### マイナーバージョン (x.Y.z)

**対象範囲**: 機能追加・更新（新しい原則の追加、既存原則の適用範囲の拡大・明確化、
プロセス規定の追加・更新）。既存の準拠を壊さないものに限る。
意味が変わっても、既存の実装を違反にしない緩和はマイナーとする

**プロセス**:

1. PRで変更を提案
2. レビュー承認
3. バージョン更新

### メジャーバージョン (X.y.z)

**対象範囲**: 既存の実装を違反にする破壊的変更。原則の削除・意味の変更・新原則の追加・適用範囲の拡大の
いずれでも、これまで準拠していたものが違反になる場合に限りメジャーとする

**判定手順**: 改定 PR の説明に「既存実装への影響の有無とその根拠」を書き、レビュアーが区分を確認する

**標準プロセス**（Issue 先行）:

1. Issueで変更を議論
2. 承認
3. バージョン更新
4. 影響を受けるドキュメントの更新

#### 例外: 実装と不可分なメジャー改定（PR 内完結 + 事後 Issue）

実装作業中に既存原則へ抵触し、原則の改定なしにはその実装を成立させられない場合に限り、
標準プロセスの手順1（Issue 先行）を省き、改定を同じ PR 内で完結させてよい。

**適用条件**（すべて満たすこと）:

- 改定内容が、その PR の実装と不可分である（改定を外すと実装が原則違反になる、または実装の根拠が失われる）
- 改定の根拠が事実で示せる（ツールの実挙動、エラーなど。「実装を通したい」だけでは不可）
- PR レビューで承認を得る。レビュアーは、改定が実装と不可分であることを確認する（手順2は省略しない）
- 影響を受けるドキュメントを同じ PR で更新する（手順4は省略しない）

**PR に書くこと**:

- 原則を改定する旨とバージョン変更（例: 1.0.0 → 2.0.0）を PR タイトルまたは冒頭で明示する
- 抵触した原則 ID と、改定が必要な理由（根拠となる事実）
- 改定前後の要求内容の差分と、影響を受けるドキュメントの一覧
- 標準プロセスを経由しなかった旨と、事後 Issue を起票する予定である旨（起票後は番号を追記する）

**事後 Issue に残すこと**（PR 作成者が、マージ後 7 日以内に起票する）:

- 何を変更したか（旧と新の要求内容の対比）と改定理由
- 標準プロセスから逸脱した点（省いた手順）
- 改定の妥当性についてオーナーの判断を仰ぐ事項（受け入れ可否、規定の見直し要否）

**制約**: この例外は原則の改定を実装の便宜で通すための手段ではない。事後 Issue でオーナーが
改定を受け入れない場合は、改定を差し戻す。実装と不可分という前提のため、実装ごと元に戻す。
改めて原則改定が必要なら、標準プロセスで Issue から議論する。
